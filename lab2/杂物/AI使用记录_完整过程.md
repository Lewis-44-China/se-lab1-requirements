# 实验二 AI 使用记录

说明：按实验手册要求，记录每一次 AI 辅助设计的使用情况。每条记录包含使用场景、输入（提示词要点）、生成结果、优点/问题、人工修改优化后的结果，以及对应的 Git 提交。最终报告第 5 章从本文件选取代表性记录。

> **当前最终状态（2026-10-31，以此为准）**：类模型中 `TicketType 1 — 1 Waitlist`（每个票种一条候补队列）；`Waitlist 1 — * WaitlistRecord`（队列内多条候补记录）；`WaitlistRecord 1 — 0..1 Registration`；`Registration` 同时关联 `Session` 和 `TicketType`。组件图最终为总体组件图 + 领域依赖图两张；总体图的“入口接入点”只是 A0～A4 连线汇聚点，不是候补队列入口，也不是模块。`WaitlistEntry`、`WaitlistQueue`、“队列入口”等仅是讨论过程中的历史写法，不是最终模型。以下记录按时间顺序保留，便于看出修改过程。

## 使用记录 1：设计基线与模块划分初稿

- **时间**：2026-10-31
- **使用场景**：根据实验一的 49 条需求，生成实验二的设计基线，包括项目范围、8 个业务模块、2 个支撑组件、分层模块化单体架构、关键设计决策和待确认问题。
- **输入（提示词要点）**：
  - “根据实验一的活动票务与报名系统需求，梳理实验二的设计基线；必须覆盖实验一 8 个业务模块；给出模块职责、依赖、接口；给出架构风格和关键设计决策；不要修改实验一文件。”
  - 同时提供实验一 `requirements.md` 作为唯一需求输入。
- **生成结果**：产出 `lab2/00_设计基线.md` 初稿，包含：
  - 四类角色与范围；
  - 8 个业务模块（活动与场次、票种与容量、报名与支付标记、退票与候补、检票、查询与统计、留痕与权限、账号与管理员处置）；
  - 2 个支撑组件（通知、持久化与并发）；
  - 分层模块化单体架构与依赖规则；
  - 12 条关键设计决策（ADR）；
  - 数据对象初稿、状态机摘要、UI 范围、待确认问题。
- **优点/问题**：
  - 优点：一次性覆盖了实验一 8 个业务模块，给出了模块职责、依赖方向、12 条设计决策和数据对象初稿，能作为后续 UML/UI 的统一基线；对 M3/M4 的循环依赖给出了“事件驱动递补”的解法。
  - 问题：初稿把“审计”单列为支撑组件，与实验一已有的“留痕与权限”模块职责重复；另外检票人员账号、候补重入、活动“进行中”触发这三个政策点实验一没有写死，AI 只能给假设，必须由人确认。
- **人工修改优化后的结果**：
  - 将审计归入 M7“留痕与权限”，支撑组件由 3 个收敛为 2 个（通知、持久化/并发）；
  - 确认检票人员账号由管理员预创建，不开放自助注册；
  - 确认候补取消后在截止前、且未生成报名记录时可重新加入，按新入队时间排队尾；
  - 确认活动“进行中”由最早场次的检票开放时间触发，定时任务推进。
- **对应 Git 提交**：AI 初稿 `a636950`；人工确认修改 `4e8a1ae`。

## 使用记录 3：按角色入口与共享能力重构组件图

- **时间**：2026-10-31
- **使用场景**：用户对使用记录 2 的组件图提出设计判断，要求按角色解耦、把 M7 作为业务约束、区分共享数据/共享功能块，并统一“读/写都有入口控制”的操作模型。AI 根据这些判断重构设计基线和组件图。
- **输入（用户反馈要点，按原意记录）**：
  - 组件图过于混乱，一个很大原因是业务模块把不同角色混在一起；M8 把账号、管理员处置等汇聚成一个模块，导致所有角色都连它。
  - M7 留痕与权限不是与业务无关，它是对业务模块的约束，直接放到“横切与支撑”里不准确。
  - 共享要区分：票种/容量这类数据是共享的；退票/候补这类功能偏操作，是否共享要看入口。
  - 读查询也可以共享，只是入口不同；这样所有操作可以统一为“共享能力 + 入口控制”。
- **生成结果**：
  - `00_设计基线.md` 更新为 v0.2：A0 认证入口、A1～A4 角色入口；D1～D6 共享写能力；Q1 共享只读查询；M7 业务约束；S1/S2 技术支撑。
  - `UML/UML组件图.puml` / `.png`：总体架构图（角色入口 → 共享能力 → 约束/支撑）。
  - `UML/UML组件图_领域依赖.puml` / `.png`：D1～D6 与 Q1 的依赖细节。
  - `UML/组件图说明.md`：两张图的读法、角色入口与 D/Q 对应表、M7 约束说明。
- **优点/问题**：
  - 优点：角色入口和共享能力分开，M8 不再汇聚所有角色；M7 的约束语义明确；读查询 Q1 单独只读；D3/D4 用事件避免循环依赖。
  - 问题：AI 第一版仍试图把“角色入口 → 每个 D/Q”的所有箭头画在一张图里，导致长线和交叉；最终拆成“总体架构图 + 领域依赖图”两张，并把具体的入口—能力对应放进表格，可读性才稳定。
- **人工修改优化后的结果**：
  - 用户确认的模块模型（C4）：A0～A4 角色入口、D1～D6 共享写能力、Q1 共享只读、M7 业务约束、S1/S2 技术支撑；
  - 本次重构的设计判断来自用户，AI 负责把判断落成基线、PlantUML 代码和说明文字；
  - 图从一张过密的图拆成总体与领域两张，这是根据用户“组件图主要看模块相关性”的意见做的调整。
- **对应 Git 提交**：`167b1c2`（本次重构提交）。

- **时间**：2026-10-31
- **使用场景**：用户审查 v0.2 组件图后，提出排版和技术支撑连接方式的修改意见，AI 据此调整组件图、说明文档和设计基线。
- **输入（用户反馈要点，按原意记录）**：

  - “共享能力并不是对于所有角色都全部可用，具体限制是应用层的角色入口约束。”

  - `UML/UML组件图.puml` / `.png`：UI 与 A3 改为“检票员”；增大块间距；删除 A1/A2/A4 → S1 的连线，改为 CAP → S1、CAP → S2 两条线；补充“共享能力并非对所有角色全可用”的图例。
  - `UML/UML组件图_领域依赖.puml` / `.png`：增大间距，补充共享能力可用性说明。
  - `UML/组件图说明.md`、`00_设计基线.md`：同步更新标签、技术支撑连接方式与通知设计。
- **优点/问题**：
  - 优点：图的主线更清楚，技术支撑只与共享能力相连；补充了“共享能力不是对所有角色全开放”的入口约束。

- **人工修改优化后的结果**：
  - 检票员标签、间距、S1/S2 连接方式均按用户意见调整；
  - 通知逻辑由“应用层直接调用通知”改为“共享能力写 Outbox、S1 消费”，使图与设计一致；
  - 用户提出的“共享能力并非对所有角色全可用”写入组件图图例、说明文档和设计基线 C5。
- **对应 Git 提交**：`6a6b3e1`（本次排版与支持连接调整）。

## 使用记录 5：入口连线汇聚

- **时间**：2026-10-31
- **使用场景**：用户继续审查总体组件图，认为 A0～A4 每个入口都分别连共享能力和 M7，线条仍然偏多；希望每个 A 只连出一根线，汇聚后再分别连共享能力（实线）和业务约束（虚线）。
- **输入（用户反馈要点，按原意记录）**：
  - “每个 A 都连接了共享能力和约束，能不能每个 A 都连出去一根线，然后这些线最后都汇聚在一起，链接到共享能力层和业务约束（一根虚线，一根实线）。”
- **生成结果**：
  - `UML/UML组件图.puml` / `.png`：增加“入口接入点（连线汇聚，不是模块）”；A0～A4 各连一根实线到该点；该点用一条实线连共享能力（命令/查询接口）、一条虚线连 M7（权限/审计约束）。
  - `UML/组件图说明.md`、`00_设计基线.md`：说明该点只是视觉汇聚，不是新增业务模块；1.3 表的入口—能力限制不变。
- **优点/问题**：
  - 优点：A0～A4 到共享能力/M7 的 10 条线收敛为 5 条入口线 + 1 条实线 + 1 条虚线，图明显更干净，角色入口顺序也更清楚。
  - 问题：汇聚点容易被误认为新增模块；已用“（连线汇聚，不是模块）”标注，并在图例和说明文档中写明，实际调用关系仍以 1.3 表/4.6 为准。
- **人工修改优化后的结果**：按用户意见完成汇聚；未改变 A0～A4 与 D/Q 的实际对应关系，只改变画法。
- **对应 Git 提交**：`f4bd797`（入口连线汇聚）。

## 使用记录 6：移除领域依赖图

- **时间**：2026-10-31
- **使用场景**：用户认为共享能力层已经封装为向上提供接口，内部依赖不是组件图要表达的重点；复杂性主要在角色入口的权限控制上，因此建议不再单独保留领域依赖图。
- **输入（用户反馈要点，按原意记录）**：
  - “领域依赖图是不是就不需要了？我们现在封装起来了，就是把共享能力提供向上的接口，内部关系其实不重要。我们的复杂性就是在角色入口的权限控制上了，能力层就是共享的能力罢了。”
- **AI 的判断与处理**：
  - 同意从**组件视图**上移除：组件图应表达“角色入口 → 共享能力接口”的封装关系，内部依赖属于实现细节，单独画第二张组件图会让层次变乱。
  - 但内部依赖仍影响实现，不能完全丢掉：D3/D4 的事件解耦、D4 释放名额、D5 更新报名状态、Q1 只读等，保留为 `组件图说明.md` 中的文字表，并在类图/时序图中体现。
  - 将 `UML组件图_领域依赖.puml/.png` 移到 `lab2/杂物/` 留档，不再放入 `UML/` 交付目录；报告只引用总体组件图。
- **生成结果**：
  - `UML/组件图说明.md`：移除第二张组件图，改成“共享能力内部依赖（文字表）”。
  - `00_设计基线.md`：交付清单移除领域依赖图，注明内部依赖写在 4.6 与报告表格。
  - `lab2/杂物/说明.md`：说明留档原因。
- **优点/问题**：
  - 优点：组件图聚焦“入口约束 + 能力封装”，不再用两张图讲同一层；复杂度集中到角色入口和权限控制上，符合当前设计重点。
  - 问题：内部依赖从图中移除后，读者可能忽略 D3/D4 的事件解耦；已用文字表、类图和时序图补足，并在说明中明确。
- **人工修改优化后的结果**：按用户意见移除主交付物中的领域依赖图，保留文字表和留档图；未改变共享能力的实际依赖设计。
- **对应 Git 提交**：`2ffed7c`（移除领域依赖图）。

## 使用记录 9：类图人工审查与调整

- **时间**：2026-10-31
- **使用场景**：用户审查类图初稿后，提出三点修改：组织者不只是创建活动，还可以修改/管理；每个票种对应一条候补队列，票种与队列是 1-1；四个角色应上下对齐成一列。
- **输入（用户反馈要点，按原意记录）**：
  - “组织者不止是创建活动，还可以修改活动；横线上的操作是不全的。”
  - “每一个票的种类都只对应了一个候补序列吧，这个是 1-1 的关系吧。”
  - “整个图是不是可以把四种角色排成上到下一列对齐，这样会清晰一些。”
