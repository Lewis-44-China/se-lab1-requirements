# 组件图说明

对应源文件：`UML组件图.puml`；导出图：`UML组件图.png`。

## 1. 这张图回答什么

组件图是**结构性（静态）图**，回答：

- 系统由哪些模块/组件组成？
- 它们之间谁依赖谁？
- 依赖是同步调用、只读查询，还是通过基础设施接口？

本图把系统分为三层：表现层、业务模块、横切与支撑；底层是 MySQL。

## 2. 图例

| 符号 | 含义 |
|---|---|
| 实线箭头 | 同步调用；调用方等待被调用方返回 |
| 虚线箭头 | 只读查询，或对基础设施/横切能力的依赖 |
| `M1`～`M8` | 实验一的 8 个业务模块 |
| `S1`、`S2` | 支撑组件：通知、持久化与并发 |
| `M7` | 实验一的“留痕与权限”模块，提供审计与权限接口 |
| 圆柱 | MySQL 8.0 数据库 |

## 3. 关键依赖与理由

| 依赖 | 类型 | 理由 |
|---|---|---|
| Web → M1/M3/M5/M6/M7/M8 | 同步 | 页面只调用应用服务接口；M2/M4 由 M1/M3 内部调用，不直接暴露给页面 |
| M1 → M2 | 同步 | 创建活动时需要场次和票种；票种容量的写入归 M2 |
| M3 → M2 | 同步 | 报名前必须原子占用名额，避免超发 |
| M3 → M4 | 同步 | 名额已满时，报名流程需要把用户加入候补队列 |
| M4 → M2 | 同步 | 退票/候补取消释放名额 |
| M5 → M3 | 同步 | 检票需要查询报名记录，并在通过后把报名记录改为“已检票” |
| M8 → M1 | 同步 | 管理员紧急取消活动，状态变更归 M1 |
| M8 → M4 | 同步 | 管理员强制退票，退款流程归 M4 |
| M8 → M6 | 同步 | 管理员查看全平台数据，查询归 M6（只读） |
| M6 ⇢ M1/M3/M5 | 只读 | 查询与统计只读取，不修改业务数据 |
| 业务模块 ⇢ M7 | 虚线 | 审计和权限是横切能力；M7 不反向依赖业务模块 |
| 业务模块 ⇢ S1 | 虚线 | 通知在业务事务提交后发送，不阻塞业务 |
| 业务模块 ⇢ S2 | 虚线 | 仓储、事务、Outbox 由 S2 提供，业务模块不直接写 SQL |

## 4. 为什么这样设计

1. **分层模块化单体**：一个部署单元，模块边界清晰；名额、报名、退款、递补可以在单库事务中完成。
2. **查询只读**：M6 只读 M1/M3/M5，不反向被依赖，避免查询逻辑影响写业务。
3. **M3/M4 不循环依赖**：M3 同步调用 M4 入队；M4 退票后只写 Outbox 事件，由 M3 的递补编排器消费，因此编译期依赖只有 M3 → M4。
4. **横切能力单独放**：M7、S1、S2 不与业务模块形成双向依赖；业务模块通过接口调用，便于替换实现。
5. **页面不直接访问数据库**：Web 只调用应用服务，权限和数据范围在服务端统一校验。

## 5. 与实验一模块的对应

| 实验一模块 | 图中组件 |
|---|---|
| 活动与场次 | M1 |
| 票种与容量 | M2 |
| 报名与支付标记 | M3 |
| 退票与候补 | M4 |
| 检票 | M5 |
| 查询与统计 | M6 |
| 留痕与权限 | M7 |
| 账号与管理员处置 | M8 |

## 6. 读图时重点看

1. 8 个业务模块是否都在图里；
2. 依赖是否单向、有没有循环；
3. 查询模块是否只读；
4. 页面是否直接连数据库；
5. M3/M4 的入队与递补是否分开处理。
