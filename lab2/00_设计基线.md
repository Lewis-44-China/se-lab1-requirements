## 1. 项目与范围

### 1.1 项目

**活动票务与报名系统**（沿用实验一主题 5）。系统面向活动参与者、活动组织者、检票人员和平台管理员，覆盖活动创建与审核、场次与票种、报名购票、退票与候补、检票、查询统计、审计留痕等业务。

实验二只做**设计**：模块划分、UML 图、UI 界面、设计报告。不写后端、不建数据库、不做前端实现；设计要细到能够指导实验三实现。

### 1.2 角色

| 角色 | 主要能力 | 关键约束 | 主要需求 |
|---|---|---|---|
| 参与者 | 浏览已公开活动、报名购票、候补、退票、查看已购票、发起检票请求、举报活动 | 不能修改活动；不能查看或修改他人个人信息 | REQ-002、REQ-012～REQ-017、REQ-027 |
| 活动组织者 | 创建并提交活动审核；管理自己的活动、场次、票种；查看和导出本活动名单；查看统计；申请取消活动 | 开售后不能改票价/容量；改时间/地点须重新审核；不能查看其他组织者的活动与报名 | REQ-002、REQ-006～REQ-011、REQ-030、REQ-031 |
| 检票人员 | 查看参与工作的活动；处理检票请求（通过或标记异常） | 不能修改报名状态；不能访问完整名单；不能看完整手机号 | REQ-002、REQ-003、REQ-014～REQ-017 |
| 平台管理员 | 审核活动、处理举报、封禁账号、查看全平台数据、紧急取消活动、强制退票 | 不能修改用户个人信息；查看个人信息仅限运营、举报、封禁所需 | REQ-002、REQ-018、REQ-041、REQ-048 |

### 1.3 范围内

- 活动与场次：创建、提交审核、审核通过/驳回、发布、修改、取消、状态推进；
- 票种与容量：VIP/普通票、价格、容量、余票、名额占用与释放；
- 报名与支付标记：报名即购票、支付标记、报名记录、次数/票数限制、幂等；
- 退票与候补：退票截止、候补入队、FIFO、自动递补、候补失败/取消与退款；
- 检票：检票请求、人工勾选、异常标记、重复检票、未检票终态；
- 查询与统计：活动查询、名单导出、报名人数/出席率/退票率统计；
- 留痕与权限：关键操作留痕、保存期限、按角色可见、RBAC 与数据范围；
- 账号与管理员处置：注册登录、封禁、举报处理、强制退票、紧急取消；
- 通知：审核结果、活动时间变更、候补递补、强制退票等站内消息。

### 1.4 范围外

- 真实支付渠道、实名核验、线下闸机/二维码验票（REQ-001）；
- 活动多组织者共管（REQ-042 已拒绝）；
- 代报名、一次购买多张票（REQ-027）；
- 找回密码、自助修改个人信息（REQ-002、REQ-047 未提供）；
- 外部短信/邮件/推送通知（本设计采用站内消息，见 REQ-028）；
- 生产级部署、高可用集群、分布式事务（课程项目不要求）。

## 2. 设计目标与质量约束

### 2.1 设计目标

1. **可指导实现**：模块边界、接口、类、数据表、状态机、关键流程完整，实验三可以照着实现。
2. **覆盖实验一**：实验一的 8 个业务模块全部有落点，49 条需求可追溯到设计元素。
3. **规则可验证**：不超发、不重复报名、状态合法、权限不越界、关键操作留痕。
4. **角色差异可见**：UI 和权限设计能看出四类角色看到什么、能做什么、不能做什么。

## 3. 架构风格

### 3.1 选择：分层模块化单体

系统采用**分层模块化单体**：部署为一个应用，但代码按业务模块严格分边界。选择理由：

- 课程项目规模有限，单体部署和调试成本低；
- 名额扣减、报名、退款、候补递补需要**强事务一致性**，单库事务最简单可靠；
- 模块边界清晰，后续若拆服务，已有接口和边界；
- 避免微服务带来的网络调用、分布式事务、运维复杂度。

**不选微服务**：为一个课程项目引入服务注册、网关、分布式事务不划算，且会削弱“不超发”这一核心规则的可验证性。

**不选纯 MVC**：MVC 只解决表现层组织，不能表达领域规则、状态机、模块依赖和并发控制；实验二需要的是完整设计，不只是页面分层。

### 3.2 分层

| 层 | 职责 | 允许依赖 | 典型内容 |
|---|---|---|---|
| 表现层 | 页面、路由、表单校验、权限入口显隐 | 应用层 | Web 前端、控制器、视图模型 |
| 应用层 | 用例编排、事务边界、跨模块协调 | 领域层、支撑组件接口 | 报名服务、退票服务、审核服务 |
| 领域层 | 实体、值对象、状态机、业务规则 | 不依赖框架/数据库 | 活动、场次、票种、报名记录、候补记录 |
| 基础设施层 | 持久化、事务、锁、通知、审计存储、定时任务 | 实现上层定义的接口 | Repository、MySQL、Outbox、Scheduler |

依赖方向：**表现层 → 应用层 → 领域层**；基础设施层实现接口，被上层依赖。领域层不出现 SQL、HTTP、框架注解。

### 3.3 依赖规则

1. 表现层只调用应用服务，不直接访问数据库或仓储。
2. 应用层负责用例编排和事务边界，不承载核心业务规则；核心规则在领域层。
3. 领域层通过仓储接口访问持久化，不知道 MySQL 的存在。
4. 跨模块写操作只能调用对方提供的应用接口，不直接改对方表。
5. 模块依赖必须是**有向无环图（DAG）**，禁止循环依赖。
6. 查询与统计模块只读，不产生业务副作用。
7. 通知、审计等横切能力通过接口调用；通知在业务事务提交后发送。

```
  ├── M3 报名与支付标记 ──> M2、M4
  ├── M4 退票与候补 ──> M2
  ├── M5 检票 ──> M3

M1、M3、M4、M5、M8 ──────────> S1（通知）
所有模块 ─────────────────────> S2（持久化/并发）
```

**关于 M3 与 M4 的循环依赖**：M3 报名满员时需要调用 M4 入队（M3 → M4）；退票后需要递补并生成报名记录（看起来 M4 → M3）。为避免循环，设计为：

- M3 → M4：同步调用 `enqueue()`；
- M4 退票释放名额后，只发布 `CapacityReleased` 事件（写入 Outbox），**不直接调用 M3**；
- M3 的递补编排器消费事件，调用 M4 的 `promoteNext()` 取得队首，再创建报名记录、占用名额、更新候补状态；
- 这样编译期依赖只有 M3 → M4，M4 不反向依赖 M3。

## 5. 模块交互与关键流程

### 5.1 报名成功

1. 表现层提交报名请求（携带请求幂等号）。
2. 应用层校验登录、角色、报名时间（服务器时间，含截止时刻）。
3. M3 按 `(账号, 场次)` 查重；已存在则返回首次结果（幂等）。
4. M3 调用 M2 `tryOccupy(票种)` 原子扣减名额；失败则进入满员分支。
5. 成功：创建报名记录（状态“已购票”、支付标记“已支付”、金额快照），写审计；事务提交后返回成功。

### 5.2 满员与候补

1. M2 原子扣减失败，返回“名额已满”。
2. 系统询问用户是否候补；用户选择候补并完成支付标记。
3. M3 调用 M4 `enqueue()`；M4 按票种写入候补记录（状态“候补中”，记录入队时间、支付金额）。
4. 写审计；事务提交后返回候补成功。

### 5.3 退票与自动递补

1. 参与者发起退票；M4 校验退票截止、报名状态、是否已检票等规则。
2. M4 更新报名记录为“自行取消”，调用 M2 `release()` 释放名额，写审计。
3. 同一事务写入 `CapacityReleased` 事件到 Outbox。
4. 事务提交后，Outbox 投递事件；M3 递补编排器消费：
   - 调用 M4 `promoteNext(票种)` 取得队首候补记录；
   - M2 原子占用名额；
   - 创建新的报名记录（已购票、已支付），更新候补记录为“已递补”；
   - 写审计，写通知 Outbox；
   - 若占用失败（并发），重试下一位或回滚本次递补。
5. 通知组件发送站内消息；失败重试，不阻塞业务事务。

### 5.4 活动审核

1. 组织者创建活动（草稿），填写活动级、场次级、票种级字段。
2. 提交审核：M1 校验必填字段，创建审核申请，活动状态“待审核”。
3. 管理员审核：通过则活动“公开”；驳回则回到“草稿”，记录审核意见。
4. 修改时间/地点、开售前修改容量/票价：创建新的修改审核申请，重新走审核；开售后容量/票价禁止修改。
5. 审核结果写审计，并通知组织者。

### 5.5 检票

1. 参与者在检票开放时间发起检票请求；M5 校验报名状态、时间窗。
2. 检票人员在检票工作台处理：通过则请求“通过”，报名记录转“已检票”；凭证不符则请求“异常”，报名记录不变。
3. 重复检票只有第一次有效，后续提示“已检票”，不再留痕、不禁止入场。
4. 场次结束后未检票的报名记录转“未检票”终态；缺席不释放名额。

### 5.6 管理员处置

- 封禁/解封账号：M8 更新账号状态，写审计；
- 处理举报：M8 更新举报状态，必要时联动 M1 取消活动或 M8 封禁账号；
- 强制退票：M8 调用 M4 的退款流程，写审计、通知参与者；
- 紧急取消活动：M8 调用 M1 取消活动，触发全部报名记录“活动取消”与退款；
- 查看全平台数据：M8 调用 M6 的只读查询，按管理员数据范围返回。

## 6. 关键设计决策（ADR）

### ADR-01 采用分层模块化单体

- **决策**：一个部署单元，按 8 个业务模块 + 2 个支撑组件分边界，内部分四层。
- **理由**：强事务一致性、开发部署简单、边界清晰、便于后续拆分。
- **代价**：模块边界需要靠规范约束；通过依赖规则、接口和代码评审保证。

### ADR-02 关系型数据库 + 单库事务

- **决策**：使用 MySQL 8.0（InnoDB，utf8mb4）作为主要存储；关键业务在单库事务内完成。
- **理由**：名额扣减、报名、退款、递补需要 ACID；唯一约束和行锁可直接支撑幂等与并发控制。
- **代价**：水平扩展能力有限；课程项目规模不需要。

### ADR-03 名额原子扣减

- **决策**：票种表维护 `occupied`，使用条件更新：

```sql
UPDATE ticket_type
SET occupied = occupied + 1
WHERE id = ? AND occupied < capacity;
-- 影响行数为 1 表示成功，0 表示已满
```

- **理由**：避免“先查余票再更新”的竞态；由数据库保证原子性。
- **兜底**：唯一约束防止重复报名；事务失败回滚；释放名额使用对称的条件更新。

### ADR-04 报名幂等

- **决策**：
  - `registration` 表对 `(account_id, session_id)` 建唯一约束；
  - 请求携带 `request_id`，`registration.request_id` 建唯一约束；
  - 重复请求在事务内命中唯一约束或查到已有记录时，返回首次结果，不重复扣名额。
- **理由**：REQ-033 要求重复提交只生成一条记录；网络重试和连续点击都可能重复提交。

### ADR-05 状态机放在领域层

- **决策**：活动、报名记录、候补记录使用封闭枚举 + 显式转换方法；非法转换抛出业务异常。
- **理由**：REQ-021～REQ-023 要求状态封闭、终态不可再变；把规则放在领域层，避免各个入口各写一套。
- **实现提示**：状态转换方法内校验前置条件（如退票截止、检票时间窗），不依赖 UI 判断。

### ADR-06 审计追加式、同事务写入

- **决策**：`audit_log` 只追加，不更新、不删除；关键业务操作与审计记录在同一事务中提交。
- **理由**：REQ-039～REQ-041 要求关键操作留痕、保存 6 个月、按角色可查；同事务避免“业务成功但没留痕”。
- **保留策略**：至少保留 6 个月；课程实现不自动删除，预留归档任务。
- **通知例外**：REQ-028 明确“通知本身不留痕”，通知失败按系统异常处理，不写审计。

### ADR-07 RBAC + 数据范围

- **决策**：角色决定可执行操作，数据范围决定可见记录；两者在应用层统一校验。
- **理由**：REQ-002、REQ-003、REQ-045 要求不同角色可见范围不同；仅靠 UI 隐藏按钮不安全。
- **实现提示**：所有查询带数据范围条件；手机号等敏感字段在返回前脱敏；管理员也不能修改用户个人信息。

### ADR-08 候补 FIFO + 事件驱动递补

- **决策**：候补按票种分别排队，按 `created_at, id` 升序；退票释放名额后通过 Outbox 事件触发递补。
- **理由**：REQ-019/020 要求先到先得、自动递补；事件解耦 M3/M4，避免循环依赖。
- **并发**：递补时重新原子占用名额；占用失败则尝试下一位，保证不超发。

### ADR-09 通知走 Outbox，事务提交后发送

- **决策**：业务事务内写 `outbox_message`；后台任务投递到站内消息表；失败重试。
- **理由**：通知失败不能回滚报名/退票；但通知也不能丢。Outbox 兼顾一致性与可靠性。
- **范围**：审核结果、活动时间变更、候补递补、强制退票；仅站内消息。

### ADR-10 服务器时间 + 定时任务

- **决策**：所有截止判断使用服务器时间；定时任务每分钟推进活动/场次状态、处理候补截止与未检票终态。
- **理由**：REQ-034 要求以服务器时间为准；REQ-021/022 的状态需要时间推动；定时任务与请求时校验双保险。

### ADR-11 UI 角色化、静态设计

- **决策**：一个 Web 应用，按角色显示不同导航和页面；实验二交付静态高保真界面，不写前端代码。
- **理由**：实验二要求 UI 设计而非实现；角色差异和数据可见性必须在界面中体现。

### ADR-12 数据存储：关系型，不用 NoSQL

- **决策**：账号、活动、场次、票种、报名、候补、检票、审核、举报、通知、审计全部落关系表；JSON 仅用于少量扩展字段（如活动标签）。
- **理由**：业务关系明确、需要事务和唯一约束；NoSQL 不适合名额扣减和强一致报名。

## 8. 状态机（摘要）

### 8.1 活动

```
草稿 → 待审核 → 公开 → 进行中 → 已结束
  ↑        │
  └────────┘（驳回退回草稿）

任意非终态 → 已取消（管理员直接取消；组织者取消需审批）
```

- 终态：已结束、已取消；已取消不得回到草稿。
- 活动取消 → 全部场次取消；场次取消不影响活动状态（即使全部场次取消，活动也不自动取消）。

### 8.2 报名记录

```
已购票 → 已检票 → 正常结束
已购票 → 自行取消（参与者退票 / 管理员强制退票）
已购票 → 未检票（场次结束仍未检票）
已购票 / 已检票 → 活动取消（活动取消时退款）
```

- 终态：正常结束、自行取消、未检票、活动取消；终态不可再变。
- 管理员强制退票进入“自行取消”终态，名额回退、退款、通知、留痕。

### 8.3 候补记录

```
候补中 → 已递补（生成“已购票”报名记录）
候补中 → 自行取消（参与者取消，退全款）
候补中 → 候补失败（候补截止仍未递补，退全款）
```

- 终态：已递补、自行取消、候补失败；终态不可再变。
