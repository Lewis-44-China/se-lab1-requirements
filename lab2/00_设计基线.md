## 1. 项目与范围

### 1.1 项目

**活动票务与报名系统**（沿用实验一主题 5）。系统面向活动参与者、活动组织者、检票人员和平台管理员，覆盖活动创建与审核、场次与票种、报名购票、退票与候补、检票、查询统计、审计留痕等业务。

实验二只做**设计**：模块划分、UML 图、UI 界面、设计报告。不写后端、不建数据库、不做前端实现；设计要细到能够指导实验三实现。

### 1.2 角色

| 角色 | 主要能力 | 关键约束 | 主要需求 |
|---|---|---|---|
| 参与者 | 浏览已公开活动、报名购票、候补、退票、查看已购票、发起检票请求、举报活动 | 不能修改活动；不能查看或修改他人个人信息 | REQ-002、REQ-012～REQ-017、REQ-027 |
| 活动组织者 | 创建并提交活动审核；管理自己的活动、场次、票种；查看和导出本活动名单；查看统计；申请取消活动 | 开售后不能改票价/容量；改时间/地点须重新审核；不能查看其他组织者的活动与报名 | REQ-002、REQ-006～REQ-011、REQ-030、REQ-031 |
| 检票人员 | 查看参与工作的活动；处理检票请求（通过或标记异常） | 不能修改报名状态；不能访问完整名单；不能看完整手机号 | REQ-002、REQ-003、REQ-014～REQ-017 |
| 平台管理员 | 审核活动、处理举报、封禁账号、查看全平台数据、紧急取消活动、强制退票 | 不能修改用户个人信息；查看个人信息仅限运营、举报、封禁所需 | REQ-002、REQ-018、REQ-041、REQ-048 |

**账号产生方式（2026-10-31 确认）**：参与者、组织者注册时选择身份；管理员账号由系统预创建；检票人员账号由管理员预创建/分配，不开放自助注册。

### 1.3 范围内

- 活动与场次：创建、提交审核、审核通过/驳回、发布、修改、取消、状态推进；
- 票种与容量：VIP/普通票、价格、容量、余票、名额占用与释放；
- 报名与支付标记：报名即购票、支付标记、报名记录、次数/票数限制、幂等；
- 退票与候补：退票截止、候补入队、FIFO、自动递补、候补失败/取消与退款；
- 检票：检票请求、人工勾选、异常标记、重复检票、未检票终态；
- 查询与统计：活动查询、名单导出、报名人数/出席率/退票率统计；
- 留痕与权限：关键操作留痕、保存期限、按角色可见、RBAC 与数据范围；

- 通知：审核结果、活动时间变更、候补递补、强制退票等站内消息。

## 2. 设计目标与质量约束

### 2.1 设计目标

1. **可指导实现**：模块边界、接口、类、数据表、状态机、关键流程完整，实验三可以照着实现。
2. **覆盖实验一**：实验一的 8 个业务模块全部有落点，49 条需求可追溯到设计元素。
3. **规则可验证**：不超发、不重复报名、状态合法、权限不越界、关键操作留痕。
4. **角色差异可见**：UI 和权限设计能看出四类角色看到什么、能做什么、不能做什么。
5. **共享能力有入口控制**：同一底层能力可被多个角色使用，但每个角色只能从自己的入口、按自己的权限和数据范围调用。

### 2.2 质量约束

| 约束 | 来源 | 设计应对 |
|---|---|---|
| 报名接口性能：1 万条报名、50 并发，100 次请求至少 95 次在 1 秒内成功 | REQ-043、REQ-044 | 关键路径只做必要查询；名额原子更新；索引覆盖；避免长事务 |
| 报名持久化：事务提交后崩溃不丢；未提交视为未发生 | REQ-046 | 单库事务；提交后才返回成功；通知等副作用走 outbox |
| 名额并发：最后名额仅一人成功，不超发 | REQ-032 | 票种行原子扣减；唯一约束兜底；失败进入候补询问 |
| 报名幂等：重复请求只生成一条记录 | REQ-033 | 唯一约束 + 请求幂等号；重复请求返回首次结果 |
| 口令安全：口令非明文存储 | REQ-045 | 使用 bcrypt/Argon2 等带盐哈希；不存明文 |
| 手机号可见性：完整版仅管理员与本人 | REQ-003、REQ-045 | 数据范围过滤 + 视图脱敏；组织者/检票人员只看遮挡版 |
| 审计：关键操作留痕，保存 6 个月 | REQ-039～REQ-041 | 追加式审计表；关键操作同事务写入；按角色过滤查询 |
| 时间判定：以服务器时间为准，含截止时刻 | REQ-034 | 统一服务器时间；截止比较使用 `<=`；定时任务推进状态 |
| 状态合法：活动/报名/候补状态封闭集合 | REQ-021～REQ-023 | 领域层状态机；非法转换直接拒绝 |

## 3. 架构风格

### 3.1 选择：分层模块化单体

系统采用**分层模块化单体**：部署为一个应用，但代码按“角色入口 + 共享能力”严格分边界。选择理由：

- 课程项目规模有限，单体部署和调试成本低；
- 名额扣减、报名、退款、候补递补需要**强事务一致性**，单库事务最简单可靠；
- 角色入口和共享领域边界清晰，后续若拆服务，已有接口和边界；
- 避免微服务带来的网络调用、分布式事务、运维复杂度。

**不选微服务**：为一个课程项目引入服务注册、网关、分布式事务不划算，且会削弱“不超发”这一核心规则的可验证性。

**不选纯 MVC**：MVC 只解决表现层组织，不能表达领域规则、状态机、模块依赖和并发控制；实验二需要的是完整设计，不只是页面分层。

### 3.2 分层与统一操作模型

```
表现层
  UI-参与者 / UI-组织者 / UI-检票 / UI-管理员 / 登录注册

应用层（入口）
  A0 认证入口（共享）
  A1 参与者应用 / A2 组织者应用 / A3 检票员应用 / A4 管理员应用

共享能力层
  写能力：D1～D6（拥有数据与业务不变量）
  读能力：Q1 查询与统计（只读）

业务约束
  M7 留痕与权限

技术支撑
  S1 通知 / S2 持久化与并发
  MySQL 8.0
```

**统一操作模型**：

```
角色入口 A0～A4
      ↓
M7 权限校验 + 数据范围
      ↓
共享能力
  ├─ 写：D1～D6（事务、不变量、状态机）
  └─ 读：Q1（只读、跨域查询、字段脱敏）
      ↓
S2 持久化/并发 → MySQL
```

统一的是“**入口 → 约束 → 共享能力**”这个模式；不统一的是读写实现：

- **写操作**：共享内部实现，但对外暴露**有明确前置条件的独立命令**，因为不同入口的权限和前置条件不同；
- **读操作**：共享一个查询服务，参数化 `DataScope`（数据范围），因为查询本质相同，只是范围和字段不同。

**共享能力不是对所有角色全部可用**：同一个 D/Q 能力在不同入口下的权限、前置条件和数据范围不同；入口约束在 A0～A4 + M7 中落地，共享能力本身不假设所有角色都能调用。

### 3.3 依赖规则

1. 表现层只调用应用层入口，不直接访问数据库或仓储。
2. 应用层负责用例编排、权限入口和事务边界，不承载核心业务规则；核心规则在共享领域模块。
3. 共享领域模块拥有自己的数据和不变量；其他模块只能通过其应用接口访问，不直接改对方表。
4. Q1 只读，不产生业务副作用；查询结果的字段脱敏和数据范围由 M7 策略 + Q1 查询条件共同保证。
5. M7 是业务约束，不是技术支撑；A0～A4 的每个用例执行前校验权限，关键操作写审计。
6. S1、S2 是技术支撑，不反向依赖业务模块。
7. 模块依赖必须是**有向无环图（DAG）**，禁止循环依赖。
8. 写操作的事务边界在应用层；领域服务不自己提交事务。
9. 技术支撑只连共享能力：S2 提供仓储/事务/Outbox；S1 消费 Outbox 通知事件，不直接依赖角色入口。

## 5. 模块交互与关键流程

### 5.1 报名成功

1. UI-参与者 → A1，提交报名请求（携带请求幂等号）。
2. A1 → M7：校验登录、角色、数据范围。
3. A1 → D3：按 `(账号, 场次)` 查重；已存在则返回首次结果（幂等）。
4. D3 → D2 `tryOccupy(票种)` 原子扣减名额；失败则进入满员分支。
5. 成功：D3 创建报名记录（已购票、已支付、金额快照），写审计；事务提交后返回成功。

### 5.2 满员与候补

1. D2 原子扣减失败，返回“名额已满”。
2. A1 询问用户是否候补；用户选择候补并完成支付标记。
3. A1 → D4 `enqueue()`；D4 按票种写入候补记录（候补中，记录入队时间、支付金额）。
4. 写审计；事务提交后返回候补成功。

### 5.3 退票与自动递补

1. 参与者退票：A1 → D4 `refundByParticipant()`；管理员强制退票：A4 → D4 `forceRefundByAdmin()`。
2. D4 校验各自前置条件：参与者退票截止；管理员按 REQ-048；两者共用内部 `releaseSeatAndRefund()`。
3. D4 更新报名记录状态（自行取消），D4 → D2 `release()` 释放名额，写审计。
4. 同一事务写入 `CapacityReleased` 事件到 Outbox。
5. 事务提交后，D3 递补编排器消费事件：
   - D4 `promoteNext(票种)` 取得队首候补记录；
   - D2 原子占用名额；
   - D3 创建新的报名记录（已购票、已支付），D4 更新候补记录为“已递补”；
   - 写审计，写通知 Outbox；
   - 若占用失败（并发），尝试下一位或回滚本次递补。
6. D3/D4 在事务内写通知事件；S1 消费 Outbox 投递站内消息；失败重试，不阻塞业务事务。

### 5.4 活动审核

1. A2 → D1：创建活动（草稿），填写活动级、场次级、票种级字段；D1 调用 D2 创建票种。
2. A2 → D1：提交审核，D1 校验必填字段，创建审核申请，活动状态“待审核”。
3. A4 → D1：审核通过则活动“公开”；驳回则回到“草稿”，记录审核意见。
4. 修改时间/地点、开售前修改容量/票价：A2 → D1 创建新的修改审核申请；开售后容量/票价禁止修改。
5. 审核结果写审计；D1 在事务内写通知事件，S1 消费 Outbox 通知组织者。

### 5.5 检票

1. 参与者发起检票：A1 → D5 `requestCheckIn()`；D5 校验报名状态、检票时间窗。
2. 检票人员处理：A3 → D5 `processCheckRequest()`；通过则请求“通过”，D5 → D3 将报名记录转“已检票”；凭证不符则请求“异常”，报名记录不变。
3. 重复检票只有第一次有效，后续提示“已检票”，不再留痕、不禁止入场。
4. 场次结束后未检票的报名记录由系统转“未检票”终态；缺席不释放名额。

### 5.6 查询与统计

1. A1/A2/A3/A4 → M7：取得数据范围策略。
2. A1/A2/A3/A4 → Q1：按 `Principal` + `DataScope` 查询。
3. Q1 只读 D1/D3/D5/D6，返回结果前按角色脱敏（如手机号遮挡）。
4. 查询不修改业务数据；名单导出只包含姓名、场次、票种，不含完整手机号。

### 5.7 管理员处置

- 创建检票账号：A4 → D6，写审计；
- 封禁/解封：A4 → D6 更新账号状态，写审计；
- 处理举报：A4 → Q1/D1 查询相关活动/账号，必要时 A4 → D1 取消活动或 A4 → D6 封禁，写审计；
- 强制退票：A4 → D4 `forceRefundByAdmin()`，写审计；D4 写通知事件，S1 消费 Outbox 通知参与者；
- 紧急取消活动：A4 → D1 取消活动，触发全部报名记录“活动取消”与退款；
- 查看全平台数据：A4 → Q1，按管理员数据范围返回；
- 审计查询：A4 → M7 审计查询接口，按 REQ-041 过滤。

## 6. 关键设计决策（ADR）

### ADR-01 采用分层模块化单体

- **决策**：一个部署单元，按“角色入口 + 共享能力 + 约束/支撑”分边界。
- **理由**：强事务一致性、开发部署简单、边界清晰、便于后续拆分。
- **代价**：模块边界需要靠规范约束；通过依赖规则、接口和代码评审保证。

### ADR-02 关系型数据库 + 单库事务

- **决策**：使用 MySQL 8.0（InnoDB，utf8mb4）作为主要存储；关键业务在单库事务内完成。
- **理由**：名额扣减、报名、退款、递补需要 ACID；唯一约束和行锁可直接支撑幂等与并发控制。
- **代价**：水平扩展能力有限；课程项目规模不需要。

### ADR-03 名额原子扣减

- **决策**：票种表维护 `occupied`，使用条件更新：

```sql
UPDATE ticket_type
SET occupied = occupied + 1
WHERE id = ? AND occupied < capacity;
-- 影响行数为 1 表示成功，0 表示已满
```

- **理由**：避免“先查余票再更新”的竞态；由数据库保证原子性。
- **兜底**：唯一约束防止重复报名；事务失败回滚；释放名额使用对称的条件更新。

### ADR-04 报名幂等

- **决策**：
  - `registration` 表对 `(account_id, session_id)` 建唯一约束；
  - 请求携带 `request_id`，`registration.request_id` 建唯一约束；
  - 重复请求在事务内命中唯一约束或查到已有记录时，返回首次结果，不重复扣名额。
- **理由**：REQ-033 要求重复提交只生成一条记录；网络重试和连续点击都可能重复提交。

### ADR-05 状态机放在领域层

- **决策**：活动、报名记录、候补记录使用封闭枚举 + 显式转换方法；非法转换抛出业务异常。
- **理由**：REQ-021～REQ-023 要求状态封闭、终态不可再变；把规则放在领域层，避免各个入口各写一套。
- **实现提示**：状态转换方法内校验前置条件（如退票截止、检票时间窗），不依赖 UI 判断。

### ADR-06 审计追加式、同事务写入

- **决策**：`audit_log` 只追加，不更新、不删除；关键业务操作与审计记录在同一事务中提交。
- **理由**：REQ-039～REQ-041 要求关键操作留痕、保存 6 个月、按角色可查；同事务避免“业务成功但没留痕”。
- **保留策略**：至少保留 6 个月；课程实现不自动删除，预留归档任务。
- **通知例外**：REQ-028 明确“通知本身不留痕”，通知失败按系统异常处理，不写审计。

### ADR-07 角色入口 + 数据范围控制

- **决策**：角色决定可执行操作，数据范围决定可见记录；两者在应用层入口和 M7 统一校验。
- **理由**：REQ-002、REQ-003、REQ-045 要求不同角色可见范围不同；仅靠 UI 隐藏按钮不安全。
- **实现提示**：A0～A4 构造 `Principal`（账号、角色、数据范围）；M7 返回权限决策；Q1 把数据范围落到查询条件；敏感字段统一脱敏。

### ADR-08 共享能力 + 独立命令

- **决策**：共享能力放在领域模块；对外暴露有明确前置条件的独立命令，而不是一个带 `role` 参数的通用方法。
- **理由**：参与者退票、管理员强制退票、活动取消退款的入口和前置条件不同，但底层“释放名额 + 退款”逻辑相同；独立命令避免 `switch(role)` 和权限泄漏。
- **实现提示**：
  - `refundByParticipant(...)`
  - `forceRefundByAdmin(...)`
  - `refundByActivityCancellation(...)`
  - 三者共用私有 `releaseSeatAndRefund(...)`。

### ADR-09 读查询共享 + DataScope

- **决策**：查询统计放在 Q1，共享一套查询/统计口径；入口传入 `Principal` 和 `DataScope`，Q1 只读、按范围过滤、按字段脱敏。
- **理由**：读操作本质相同，拆成多个角色查询模块会重复 SQL 和统计口径；统一查询服务更容易保证统计口径一致。
- **实现提示**：Q1 使用只读查询接口/视图，不调用写仓储；查询不产生业务副作用。

### ADR-10 候补 FIFO + 事件驱动递补

- **决策**：候补按票种分别排队，按 `created_at, id` 升序；退票释放名额后通过 Outbox 事件触发递补。
- **理由**：REQ-019/020 要求先到先得、自动递补；事件解耦 D3/D4，避免循环依赖。
- **并发**：递补时重新原子占用名额；占用失败则尝试下一位，保证不超发。

### ADR-11 通知走 Outbox，事务提交后发送

- **决策**：共享能力在业务事务内写 `outbox_message`；S1 消费 Outbox 投递到站内消息表；失败重试。
- **理由**：通知失败不能回滚报名/退票；但通知也不能丢。Outbox 兼顾一致性与可靠性。
- **范围**：审核结果、活动时间变更、候补递补、强制退票；仅站内消息。
- **依赖方向**：共享能力 → S2（Outbox）；S1 消费 Outbox；S1 不直接依赖角色入口。

### ADR-12 服务器时间 + 定时任务

- **决策**：所有截止判断使用服务器时间；定时任务每分钟推进活动/场次状态、处理候补截止与未检票终态。活动进入“进行中”的触发点为**该活动最早场次的检票开放时间**（2026-10-31 确认）。
- **理由**：REQ-034 要求以服务器时间为准；REQ-021/022 的状态需要时间推动；定时任务与请求时校验双保险。

### ADR-13 UI 角色化、静态设计

- **决策**：一个 Web 应用，按角色显示不同导航和页面；实验二交付静态高保真界面，不写前端代码。
- **理由**：实验二要求 UI 设计而非实现；角色差异和数据可见性必须在界面中体现。

## 8. 状态机（摘要）

### 8.1 活动

```
草稿 → 待审核 → 公开 → 进行中 → 已结束
  ↑        │
  └────────┘（驳回退回草稿）

任意非终态 → 已取消（管理员直接取消；组织者取消需审批）
```

- 终态：已结束、已取消；已取消不得回到草稿。
- “进行中”由**最早场次的检票开放时间**触发，定时任务推进（2026-10-31 确认）。
- 活动取消 → 全部场次取消；场次取消不影响活动状态（即使全部场次取消，活动也不自动取消）。

### 8.2 报名记录

```
已购票 → 已检票 → 正常结束
已购票 → 自行取消（参与者退票 / 管理员强制退票）
已购票 → 未检票（场次结束仍未检票）
已购票 / 已检票 → 活动取消（活动取消时退款）
```

- 终态：正常结束、自行取消、未检票、活动取消；终态不可再变。
- 管理员强制退票进入“自行取消”终态，名额回退、退款、通知、留痕。

### 8.3 候补记录

```
候补中 → 已递补（生成“已购票”报名记录）
候补中 → 自行取消（参与者取消，退全款）
候补中 → 候补失败（候补截止仍未递补，退全款）
```

- 终态：已递补、自行取消、候补失败；终态不可再变。
