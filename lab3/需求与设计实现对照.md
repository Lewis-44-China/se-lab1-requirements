## 3. 核心实现逻辑

### 3.1 登录、角色与封禁

- `account.phone` UNIQUE，四种角色共用一个账号空间；
- 参与者/组织者自助注册；管理员由 `bootstrap_admin` 初始化，检票员由管理员创建；
- 登录只校验手机号 + 密码，角色来自账号属性；
- 封禁后：参与者仍可查看已有票、发起检票、退票、查询、收通知；
  组织者写活动、检票员读工作台/处理/被分配、新增报名/候补均被拒绝；
- 受封禁影响的写入口使用 `PermissionService.reload_active` 重新读库，
  避免登录时的旧账号对象绕过状态变化。

### 3.2 活动、场次与审核

- 活动状态：`DRAFT → PENDING_REVIEW → PUBLISHED → ONGOING → ENDED`，
  任意非终态可进入 `CANCELLED`；
- 草稿：所有修改直接生效；
- 发布后：名称/描述/封面/标签直接生效；地点、场次时间、票价/容量生成
  MODIFY 审核；票价/容量开售后禁止（申请和审核通过双重校验）；
- 终态活动不再执行发布/修改/取消领域动作；残留审核单可由管理员关闭为
  `REJECTED`（不会自动清队列）；
- 售票截止必须早于最早场次开始；候补截止强制等于售票截止。

### 3.3 报名与名额

- 同一账号同一场次只能有一条报名记录；`(account_id, session_id)` 唯一；
- `request_id` 唯一，重复请求返回首次结果；并发同号兜底复核账号归属；
- 名额：`UPDATE ... SET occupied=occupied+1 WHERE occupied<capacity`，
  判断与扣减同一条 SQL；
- 报名、扣名额、审计在同一事务；失败回滚后用独立事务写失败审计。

### 3.4 候补与递补

- 每个票种一条队列；FIFO 按 `join_time, id`；
- 候补截止 = 售票截止，截止时刻起拒绝入队；
- 退票写 `CapacityReleased` Outbox；`PromotionService` 取队首，
  二次校验账号/名额/重复报名，成功则生成报名并置 `PROMOTED`；
- 队首失败时事件保持 `NEW`，下一轮继续尝试下一位；连续失败按重试次数处理；
- 候补取消/截止失败/活动取消/封禁都退全款，条件 UPDATE 保证只退一次；
- 同一账号同一场次只保留一个“有效票或候补”；已有候补时购买其他票种，
  需先取消候补（实现选择，见第 4 节）。

### 3.5 退票与活动取消

- 入口：参与者退票、管理员强制退票、管理员/审核/封禁/举报联动取消活动；
- 三条入口共用单条退款动作：改终态、记录退款金额/时间、释放名额、写审计；
- 参与者/强制退票写 `CapacityReleased`；活动取消不写事件，活动已终态；
- 活动取消同时把 WAITING 候补转 FAILED 并退款；并发取消用条件 UPDATE 防重复。

### 3.6 检票

- 参与者发起请求，检票员只处理请求；
- 通过：请求 `PENDING → PASSED`，报名 `PURCHASED → CHECKED_IN`；
- 异常：只改请求 `PENDING → ABNORMAL`，报名不变；
- 时间窗：检票开放时刻允许，场次结束时刻起拒绝；
- 工作台只显示报名仍为 `PURCHASED` 的请求；终态报名不可处理；
- 重复检票只有第一次有效，第二次不新增审计。

### 3.7 查询、审计与通知

- 参与者：公开活动、本人报名/候补/检票/举报/账号审计；
- 组织者：自己的活动、名单（手机号遮挡）、统计、被举报记录；
- 检票员：被分配活动、待处理请求；封禁后不可读工作台；
- 管理员：全平台、全部审计；
- 失败报名/候补留痕使用 `REGISTRATION_ATTEMPT` 对象，参与者本人可见，
  组织者不可见；
- 通知与业务同事务写入：不会丢失，但通知写入失败会回滚业务，按系统异常处理。

### 3.8 定时任务、演示数据与入口

- CLI 每次角色菜单循环前调用 `Scheduler.tick()`：
  状态推进 → 候补过期 → 报名终态 → Outbox 消费；
- 单进程菜单模型；不保证多进程同时操作同一 SQLite 库的竞态；
- `seed_demo` 用 ManualClock 调真实服务生成演示数据；空库首次启动自动生成；
- `--no-seed` 空库创建默认管理员；`--reset` 清理数据库及 `-wal/-shm`。

## 7. 架构与代码边界

- `presentation_表现层`：只做输入/展示；不直接写 SQL。
- `application_应用层`：审核/封禁/举报/递补/时间任务编排。
- `domain_共享能力层`：活动、票种、报名、候补、退款、检票、查询等业务能力。
- `common_横切能力`：权限、审计、通知。
- `infrastructure_基础设施`：SQLite、时钟、口令/金额工具。
- `container.py`：组合根，按依赖顺序装配，所有服务共享同一 `db/clock/audit`。
- 事务边界在服务层；跨服务复用 `*_conn` 方法共享连接；SQLite 不支持嵌套事务。
