# 人工审查记录

> 用途：记录本人对实验三 AI 辅助生成代码的逐层审查过程，作为实验报告
> “AI 辅助开发与人工审查”章节的事实素材。本文件不是报告正文，也不代替报告。
> 代码由 Claude Code 辅助生成；审查结论由本人作出，报告正文由本人撰写。

## 1. 审查方法

按架构层次与业务链路审查，而不是按文件顺序通读：

1. 数据层：`schema.sql` → 领域模型 `domain/models.py`；
2. 基础设施：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`；
3. 主业务链路：报名 → 退票/候补 → 检票 → 活动审核 → 查询；
4. 横切能力：`common/permissions.py`、`audit.py`、`notifications.py`；
5. 应用编排与表现层：`application/admin.py`、`scheduler.py`、`seed.py`、`presentation/cli.py`、`render.py`；
6. 测试与交付：`tests/`、打包脚本。

每个模块按同一组问题检查：输入校验、事务边界、状态迁移、权限、审计、
金额/时间格式、并发。

### 2.3 基础设施（2026-11-04）

- 范围：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`。
- 对照：设计基线 S2（持久化与并发）、REQ-045（口令与手机号）、业务截止时间。
- 结论：**通过**；审查注释已补入四个文件。
- 记录：
  - `db.py`：`isolation_level=None` + `BEGIN IMMEDIATE` 显式事务；异常 rollback、
    正常 commit；WAL + `busy_timeout` 处理并发写；`schema.sql` 的 `IF NOT EXISTS`
    可重复建表；`db.execute` 只用于无需跨表一致性的单条写入。
  - `clock.py`：所有截止判断走 `Clock.now()`；`SystemClock` 去掉微秒，与数据库
    时间格式一致；`ManualClock` 供测试/演示拨表；`parse_dt` 支持绝对格式和
    `+Nd/+Nh/+Nm`。
  - `security.py`：PBKDF2-HMAC-SHA256、16 字节盐、200000 次迭代；
    `compare_digest` 常量时间比较；手机号只接受中国大陆 11 位；脱敏保留前 3 后 4；
    金额用 `Decimal` 转“分”。
  - `errors.py`：业务异常基类与 7 个子类；`CapacityFull` 携带 `ticket_type_id`
    供候补询问。
- 注意项：
  - SQLite 不支持嵌套事务，跨服务组合统一用 `*_conn` 方法共享连接；
  - `AccountBanned` 当前未被使用，封禁由 `PermissionDenied` 表达，保留为语义预留；
  - 金额换算按 `Decimal` 默认舍入处理第三位小数，界面输入建议最多两位；
  - 时间为服务器本地时间，未处理时区；课程项目按单机本地时间运行。

### 2.4 报名链路：`tickets.py` 与 `registrations.py`（2026-11-04）

- 范围：`domain/tickets.py`、`domain/registrations.py`，以及相关调用方
  `domain/activities.py`、`presentation/cli.py`。
- 对照：活动图/时序图_报名购票、REQ-024/025/026/027/032/033/034/039。
- 结论：**通过，并修复 1 处时间窗口**。
- 记录：
  - `try_occupy`：条件 UPDATE，`rowcount == 1` 才成功，判断与扣减在同一条 SQL，
    避免“先查余票再更新”的竞态。
  - `register`：重新读账号 → 权限 → 幂等 → 售票窗口 → 同场次/候补检查 →
    扣名额 → 插入报名 → 审计，全部在同一事务；失败用 `record_standalone` 留痕。
  - 幂等：`request_id` 唯一 + `(account_id, session_id)` 唯一，
    并发下用 `IntegrityError` 兜底并回查已有记录。
  - 候补确认：服务层只抛 `CapacityFull`，CLI 询问用户后才调用
    `WaitlistService.enqueue`，没有自动候补。
- 修复：
  - 原实现只在“申请修改”时检查开售时间（`_build_ticket_updates`），
    审核通过时 `apply_modification` 不再检查；申请后拖到开售再审批会绕过
    “开售后禁改容量/票价”。
  - 已在 `apply_modification` 应用票价/容量前再次检查 `now >= sale_start`，
    并新增测试 `test_ticket_change_approved_after_sale_forbidden`（39 个测试）。

### 2.5 退票与活动取消：`domain/refunds.py`（2026-11-04）

- 范围：3 个退款入口、1 个事务内批量取消、1 个共用退款动作。
- 对照：状态图_报名记录、REQ-011/013/032/035/037/048。
- 结论：**通过**；已给每个函数补充职责注释。
- 记录：
  - `refund_by_participant`：参与者本人、已购票、未过退票截止；
    写 `CapacityReleased`，触发候补递补。
  - `force_refund`：管理员、原因必填、仅“已购票”；写事件并给购票人发
    `FORCE_REFUND` 通知。
  - `cancel_activity`：公开入口，只做权限/原因校验并开事务。
  - `cancel_activity_conn`：事务内批量取消，供审核通过、封禁组织者、举报处理复用；
    活动/场次置 `CANCELLED`、批量退款、`WAITING` 候补转 `FAILED`、通知组织者；
    不写 `CapacityReleased`。
  - `_refund_registration_conn`：所有退款共用；条件 UPDATE + 退款金额/时间 +
    释放名额 + 审计 + 可选 Outbox/通知。
- 注意：强制退票的报名状态仍记 `SELF_CANCELLED`，审计 action 用 `FORCE_REFUND`
  区分；这是实现选择，已在注释说明。

### 2.6 候补与递补：`waitlist.py`、`promotion.py`（2026-11-04）

- 范围：候补入队/取消/失败退款/递补，Outbox 消费。
- 对照：状态图_候补记录、活动图_报名购票、REQ-019/020/023/037/039。
- 结论：**通过**。
- 记录：
  - 入队：每个票种一条队列，按 `join_time/id` FIFO；同账号同场次只能有一条
    `WAITING`；有余票时拒绝候补，要求直接报名。
  - 失败退款：候补截止、场次结束、活动取消、账号封禁都汇到 `mark_failed_conn`；
    条件 UPDATE `WHERE status='WAITING'` + rowcount 检查，确保同一记录只退一次；
    统一发 `WAITLIST_FAILED` 通知并写审计。
  - 主动取消：`_mark_self_cancelled` 退全款、写审计，不发通知（用户主动操作）。
  - 递补：退票写 `CapacityReleased` → `Scheduler.tick` → `PromotionService`
    取队首 → 再次检查账号/名额/重复报名 → 生成报名记录 → 候补置 `PROMOTED`
    → 通知。
  - 事件失败重试 5 次后标记 `PROCESSED`，避免事件卡死。
