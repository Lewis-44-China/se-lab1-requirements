# 人工审查记录

> 用途：记录本人对实验三 AI 辅助生成代码的逐层审查过程，作为实验报告
> “AI 辅助开发与人工审查”章节的事实素材。本文件不是报告正文，也不代替报告。
> 代码由 Claude Code 辅助生成；审查结论由本人作出，报告正文由本人撰写。

## 1. 审查方法

按架构层次与业务链路审查，而不是按文件顺序通读：

1. 数据层：`schema.sql` → 领域模型 `domain/models.py`；
2. 基础设施：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`；
3. 主业务链路：报名 → 退票/候补 → 检票 → 活动审核 → 查询；
4. 横切能力：`common/permissions.py`、`audit.py`、`notifications.py`；
5. 应用编排与表现层：`application/admin.py`、`scheduler.py`、`seed.py`、`presentation/cli.py`、`render.py`；
6. 测试与交付：`tests/`、打包脚本。

每个模块按同一组问题检查：输入校验、事务边界、状态迁移、权限、审计、
金额/时间格式、并发。

## 2. 已完成的审查

### 2.1 `schema.sql`（2026-11-04）

- 范围：14 张业务表、CHECK 约束、UNIQUE 约束、部分唯一索引、查询索引。
- 对照：实验二类图、用例图、活动图/状态图，以及实验三的应用流程。
- 结论：**通过**。表、字段与实验二类的要求和应用流程一致。
- 记录：
  - 账号采用单表 + `role` 判别列，符合设计；
  - 活动时间细化到场次（`activity_session.start_time/end_time`），与实验二
    “活动级 time”不同，但更精确，属于可接受差异；
  - 报名/候补/检票的唯一约束与 `occupied <= capacity` 能兜住
    不超发、幂等、同一场次只能报名一次；
  - 候补记录含 `activity_id`、`session_id` 快照，与修订后的类图一致。
- 备注：审查时在 `schema.sql` 中加了逐表注释，用于标记“与实验二一致/合理差异”。

### 2.2 `domain/models.py`（2026-11-04）

- 范围：13 个枚举 + 11 个 dataclass + `from_row` 转换 + 派生属性。
- 对照：`schema.sql` 的 CHECK、实验二类图与状态图。
- 结论：**通过**；提出 1 个待核实问题（Q1），已核实。
- 审查注释：各枚举标注“一致”；`SessionStatus` 注明 `FULL` 只表示容量已满，
  候补资格由场次 `allow_waitlist` 与活动级 `waitlist_deadline` 等条件判断。
- 记录：
  - `Role`、`AccountStatus`、`ActivityStatus`、`RegistrationStatus` 与
    schema CHECK、状态图一致；
  - `WaitlistStatus`：`WAITING / PROMOTED / SELF_CANCELLED / FAILED`；
    `FAILED` 包含“候补截止未递补”和“活动取消”两种情况，与修订后的候补状态图一致；
  - `NotificationType` 包含 `ACTIVITY_CANCELLED`，与修订后的治理类图一致；
  - dataclass 字段与表字段一一对应，`from_row` 转换正确；
  - 派生属性 `TicketType.remaining`、`Registration.is_terminal`、
    `Registration.occupies_seat`、`Account.is_banned` 与业务口径一致；
  - `WaitlistRecord` 含 `activity_id`/`session_id` 快照，与 schema、类图一致。

### 2.3 基础设施（2026-11-04）

- 范围：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`。
- 对照：设计基线 S2（持久化与并发）、REQ-045（口令与手机号）、业务截止时间。
- 结论：**通过**；审查注释已补入四个文件。
- 记录：
  - `db.py`：`isolation_level=None` + `BEGIN IMMEDIATE` 显式事务；异常 rollback、
    正常 commit；WAL + `busy_timeout` 处理并发写；`schema.sql` 的 `IF NOT EXISTS`
    可重复建表；`db.execute` 只用于无需跨表一致性的单条写入。
  - `clock.py`：所有截止判断走 `Clock.now()`；`SystemClock` 去掉微秒，与数据库
    时间格式一致；`ManualClock` 供测试/演示拨表；`parse_dt` 支持绝对格式和
    `+Nd/+Nh/+Nm`。
  - `security.py`：PBKDF2-HMAC-SHA256、16 字节盐、200000 次迭代；
    `compare_digest` 常量时间比较；手机号只接受中国大陆 11 位；脱敏保留前 3 后 4；
    金额用 `Decimal` 转“分”。
  - `errors.py`：业务异常基类与 7 个子类；`CapacityFull` 携带 `ticket_type_id`
    供候补询问。
- 注意项：
  - SQLite 不支持嵌套事务，跨服务组合统一用 `*_conn` 方法共享连接；
  - `AccountBanned` 当前未被使用，封禁由 `PermissionDenied` 表达，保留为语义预留；
  - 金额换算按 `Decimal` 默认舍入处理第三位小数，界面输入建议最多两位；
  - 时间为服务器本地时间，未处理时区；课程项目按单机本地时间运行。

### 2.4 报名链路：`tickets.py` 与 `registrations.py`（2026-11-04）

- 范围：`domain/tickets.py`、`domain/registrations.py`，以及相关调用方
  `domain/activities.py`、`presentation/cli.py`。
- 对照：活动图/时序图_报名购票、REQ-024/025/026/027/032/033/034/039。
- 结论：**通过，并修复 1 处时间窗口**。
- 记录：
  - `try_occupy`：条件 UPDATE，`rowcount == 1` 才成功，判断与扣减在同一条 SQL，
    避免“先查余票再更新”的竞态。
  - `register`：重新读账号 → 权限 → 幂等 → 售票窗口 → 同场次/候补检查 →
    扣名额 → 插入报名 → 审计，全部在同一事务；失败用 `record_standalone` 留痕。
  - 幂等：`request_id` 唯一 + `(account_id, session_id)` 唯一，
    并发下用 `IntegrityError` 兜底并回查已有记录。
  - 候补确认：服务层只抛 `CapacityFull`，CLI 询问用户后才调用
    `WaitlistService.enqueue`，没有自动候补。
- 修复：
  - 原实现只在“申请修改”时检查开售时间（`_build_ticket_updates`），
    审核通过时 `apply_modification` 不再检查；申请后拖到开售再审批会绕过
    “开售后禁改容量/票价”。
  - 已在 `apply_modification` 应用票价/容量前再次检查 `now >= sale_start`，
    并新增测试 `test_ticket_change_approved_after_sale_forbidden`（39 个测试）。

## 3. 审查中发现的问题

| 编号 | 位置 | 问题 | 结论/处理 | 状态 |
|---|---|---|---|---|
| Q1 | `SessionStatus`（`domain/models.py`） | 场次“已满”是否还要区分“能候补 / 不能候补”两种？ | 不需要拆分。`FULL` 只表示容量已满；候补资格由 `allow_waitlist`、活动级 `waitlist_deadline`、票种余票、账号是否已有报名/候补、活动/场次时间共同判断（`WaitlistService._enqueue_impl`）。候补资格是按票种 + 按账号的，不是场次级二元状态。 | 已核实，审核通过；`models.py` 注释已更新 |
| Q2 | `infrastructure/db.py` | 事务能否嵌套？ | SQLite 不支持嵌套事务；当前跨服务组合统一用 `*_conn` 方法共享同一连接，未出现嵌套。 | 已说明，无需修改 |
| Q3 | `domain/errors.py` | `AccountBanned` 是否被使用？ | 当前未使用；封禁由 `PermissionService.require_active` 抛 `PermissionDenied`。保留为更细的语义预留。 | 已记录，后续可统一 |
| Q4 | `infrastructure/security.py` | 金额第三位小数如何舍入？ | 按 `Decimal` 默认舍入；界面输入建议最多两位小数。 | 已说明，无需修改 |
| Q5 | `domain/tickets.py`、`domain/activities.py` | 开售后禁改容量/票价，是否只在申请时检查？ | 原实现只在申请时检查；审核通过时若已开售会绕过。已在 `apply_modification` 应用前再次检查，并新增测试。 | 已修复 |
| Q6 | `domain/registrations.py`、`presentation/cli.py` | 满员后是否自动进入候补？ | 不自动。服务层抛 `CapacityFull`，CLI 询问用户后才调用 `WaitlistService.enqueue`。 | 已确认，无需修改 |

## 6. 一点想法

我对于软件工程的编程语言选择、编程框架的选择其实没有很深的理解；编程过程中，
对于和数据库操作接口的部分我也没有基础。这部分其实 AI 发挥了很大的作用，
我认为是一种降低了我们上手成本要求的很好的助力；但是审查其实还是需要人来看
具体实现的，尤其是设计具体的工作流程的把握。
