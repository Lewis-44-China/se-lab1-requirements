## 1. 审查方法

按架构层次与业务链路审查，而不是按文件顺序通读：

1. 数据层：`schema.sql` → 领域模型 `domain/models.py`；
2. 基础设施：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`；
3. 主业务链路：报名 → 退票/候补 → 检票 → 活动审核 → 查询；
4. 横切能力：`common/permissions.py`、`audit.py`、`notifications.py`；
5. 应用编排与表现层：`application/admin.py`、`scheduler.py`、`seed.py`、`presentation/cli.py`、`render.py`；
6. 测试与交付：`tests/`、打包脚本。

每个模块按同一组问题检查：输入校验、事务边界、状态迁移、权限、审计、
金额/时间格式、并发。

### 2.3 基础设施（2026-11-04）

- 范围：`infrastructure/db.py`、`clock.py`、`security.py`、`domain/errors.py`。
- 对照：设计基线 S2（持久化与并发）、REQ-045（口令与手机号）、业务截止时间。
- 结论：**通过**；审查注释已补入四个文件。
- 记录：
  - `db.py`：`isolation_level=None` + `BEGIN IMMEDIATE` 显式事务；异常 rollback、
    正常 commit；WAL + `busy_timeout` 处理并发写；`schema.sql` 的 `IF NOT EXISTS`
    可重复建表；`db.execute` 只用于无需跨表一致性的单条写入。
  - `clock.py`：所有截止判断走 `Clock.now()`；`SystemClock` 去掉微秒，与数据库
    时间格式一致；`ManualClock` 供测试/演示拨表；`parse_dt` 支持绝对格式和
    `+Nd/+Nh/+Nm`。
  - `security.py`：PBKDF2-HMAC-SHA256、16 字节盐、200000 次迭代；
    `compare_digest` 常量时间比较；手机号只接受中国大陆 11 位；脱敏保留前 3 后 4；
    金额用 `Decimal` 转“分”。
  - `errors.py`：业务异常基类与 7 个子类；`CapacityFull` 携带 `ticket_type_id`
    供候补询问。
- 注意项：
  - SQLite 不支持嵌套事务，跨服务组合统一用 `*_conn` 方法共享连接；
  - `AccountBanned` 当前未被使用，封禁由 `PermissionDenied` 表达，保留为语义预留；
  - 金额换算按 `Decimal` 默认舍入处理第三位小数，界面输入建议最多两位；
  - 时间为服务器本地时间，未处理时区；课程项目按单机本地时间运行。
- 第二轮复核：2026-11-05 手工验证口令/盐、时间解析、金额舍入与事务回滚，
  复核无误；另记录 Q35/Q36 两条非阻塞观察，见第 11 节。

### 2.6 候补与递补：`waitlist.py`、`promotion.py`（2026-11-04）

- 范围：候补入队/取消/失败退款/递补，Outbox 消费。
- 对照：状态图_候补记录、活动图_报名购票、REQ-019/020/023/037/039。
- 结论：**通过**。
- 记录：
  - 入队：每个票种一条队列，按 `join_time/id` FIFO；同账号同场次只能有一条
    `WAITING`；有余票时拒绝候补，要求直接报名。
  - 失败退款：候补截止、场次结束、活动取消、账号封禁都汇到 `mark_failed_conn`；
    条件 UPDATE `WHERE status='WAITING'` + rowcount 检查，确保同一记录只退一次；
    统一发 `WAITLIST_FAILED` 通知并写审计。
  - 主动取消：`_mark_self_cancelled` 退全款、写审计，不发通知（用户主动操作）。
  - 递补：退票写 `CapacityReleased` → `Scheduler.tick` → `PromotionService`
    取队首 → 再次检查账号/名额/重复报名 → 生成报名记录 → 候补置 `PROMOTED`
    → 通知。
  - 事件失败重试 5 次后标记 `PROCESSED`，避免事件卡死。
- 第二轮复核：2026-11-05 对照 REQ-019/020/023/049 复核入队条件与递补失败处理；
  补候补并发唯一约束兜底（Q48）、失败队首不消费事件（Q49），见第 16 节。

### 13.2 `capacity < occupied` 检查为什么保留

- `tickets.release()` 执行 `occupied = occupied - 1`（`WHERE occupied > 0`）；
- 余票不是独立字段，而是 `capacity - occupied` 实时计算，所以释放后立刻可见；
- 有候补：`CapacityReleased` 事件被 `PromotionService` 消费，队首重新占位；
- 无候补：事件消费时队首为空，标记为 `PROCESSED` 后结束，名额留在余票池；
- 场次状态：下一次 `Scheduler.tick` 的 `refresh_statuses()` 会把 `FULL` 重算为
  `OPEN`，不需要额外的回补操作。

### 15.4 其它确认

- 退款金额 = 报名时记录的 `payment_amount_cents`，全额退；
- 参与者退票、管理员强制退票只接受 `PURCHASED`；活动取消额外接受 `CHECKED_IN`；
- 活动取消不写 `CapacityReleased`，因为活动已终态，不再递补；
- `_refund_registration_conn` 条件 UPDATE + rowcount，保证同一条报名只退一次；
- 验证：**50 个测试全部通过，pylint 10.00/10**。

## 17. 第二轮（最终）审查：检票 `domain/checkin.py`（2026-11-05）

  的关系产生疑问。

### 17.1 为什么 `_pass` 可以改报名状态（Q51）

- REQ-014 的“检票人员不得修改报名状态”是指：系统不提供让检票员**任意选择**
  报名状态的入口。检票员的操作对象始终是 `check_request`，只有两种选择：
  - 通过 → `_pass`：请求 `PENDING → PASSED`，同时报名 `PURCHASED → CHECKED_IN`；
  - 异常 → `_mark_abnormal`：只把请求改为 `ABNORMAL`，报名完全不动。
- “通过后报名变为已检票”是 REQ-014 明确规定的**正常结果**，属于领域动作的
  受控推导，不是绕过请求直接改状态。
- 请求记录的价值：检票员的工作项、异常标记的载体、审计对象；报名状态只表达
  票的生命周期。两者分开才能记录“谁在什么时候检了哪张票”。
- 审计：发起请求写 `CHECK_REQUEST_CREATED`；通过写请求 `CHECKIN_PASSED` 和
  报名 `REGISTRATION_CHECKED_IN` 两条；异常写 `CHECKIN_ABNORMAL` 一条。

### 17.2 其它流程确认

- 发起请求：本人、参与者、`PURCHASED`、时间窗内；已有 PENDING 直接复用；
- 时间窗 `_ensure_window`：活动/场次未取消，`checkin_open_time <= now <= end_time`，
  发起和处理共用同一套判断；
- 重复检票：报名已 `CHECKED_IN` 时发起被拒绝；处理时两个 UPDATE 都带状态条件
  和 rowcount，两个检票口同时处理只有第一个成功；REQ-036 要求第二次不留痕，
  代码在进入 `_pass` 前就拒绝，不新增审计；
- 检票员查询只返回分配给自己的活动，手机号在服务层遮挡；
- 手动勾选，无二维码入口（REQ-015）。

### 17.3 Q52：并发发起请求的边界

`check_request` 没有“同一报名只能有一条 PENDING”的唯一索引。服务先查 PENDING
并复用，单进程 CLI 下不会重复；多进程/多线程同时发起理论可产生两条 PENDING。
处理第一条后，第二条再处理会提示“已检票”或只能标异常，不会把报名改成错误状态。
当前按单进程运行模型记录，不额外加索引。

## 18. 第二轮（最终）审查：活动修改、取消与审核结果（2026-11-05）

- 触发：复核活动修改的范围、取消的前置状态，以及审核通过后是否按当前

- 结论：**规则与 REQ-010/011 一致**；代码无需修改，补充审查注释；

### 18.1 活动修改范围（Q53，对照 REQ-010）

| 内容 | 草稿 DRAFT | 发布后 PUBLISHED/ONGOING |
|---|---|---|
| 名称、描述、封面、标签 | 直接生效 | 直接生效（名称归类为表面信息） |
| 地点、场次时间、检票时间 | 直接生效 | 提交 MODIFY 审核 |
| 票价、容量 | 直接生效 | 开售前提交审核；开售后禁止（申请与审核双重校验） |

### 18.2 取消的前置判断（Q54，对照 REQ-011）

- 拒绝 `CANCELLED`/`ENDED`，要求“活动存在且未结束”；
- `DRAFT`/`PUBLISHED`/`ONGOING` 都可提交取消申请，管理员审批；
- 同一活动已有 PENDING 的 CANCEL 申请时拒绝重复提交；
- “时间上是否已结束”由 `Scheduler.tick` 在每次菜单操作前推进成 `ENDED`，
  再进入取消入口；正常路径不需要在取消里再算一遍时间；
- 管理员直接取消走 `cancel_activity_conn` 的条件 UPDATE，防止并发重复取消（Q45）。

### 18.3 审核通过后的状态/时间复核（Q55）

| 审核类型 | 通过时的复核 |
|---|---|
| PUBLISH | 活动必须仍为 `PENDING_REVIEW`，防止取消/结束后被重新发布 |
| MODIFY | 重新检查 `CANCELLED`/`ENDED`；票价/容量还要检查是否已开售 |
| CANCEL | 条件 UPDATE 排除 `CANCELLED`/`ENDED`，失败则回滚整个审核事务 |

- 复核失败抛 `Conflict`/`PermissionDenied`，审核单保持 `PENDING`，管理员可改判驳回；
- 活动状态在每次菜单操作前由 tick 刷新，因此审核动作默认看到的是当前状态。

### 18.4 Q56：多进程时间边界

状态校验与审核动作之间仍有理论时间窗：例如状态刚被 tick 刷新，随后另一个进程
把活动取消/推进到结束。取消侧已有条件 UPDATE 兜底；修改侧依赖审核前读取的
状态对象。单进程菜单模型下不会发生，记录为运行模型边界，不额外加入时间计算。

- 权限仍由各服务的 `require_role/require_owner/require_active` 执行；
- 装配顺序无循环依赖；所有服务共享同一 `db/clock/audit`；
- 事务边界在各服务内部，容器不开启事务。
