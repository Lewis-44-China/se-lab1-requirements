## 1. 技术选型

| 维度 | 实验二设计 | 实验三实现 | 原因 |
|---|---|---|---|
| 架构 | 分层模块化单体 | Python 包内分层模块化单体 | 保持 A/D/Q/M/S 边界，单进程部署 |
| 存储 | MySQL 8.0 | SQLite 3 | 桌面程序零依赖；事务、唯一约束、条件更新能力足够；课程规模不需要独立数据库服务 |
| 界面 | Web 高保真 UI | 终端菜单 | 手册不强制 GUI；终端更便于逐行审查和自动化测试 |
| 通知 | Outbox + S1 | Outbox 表 + 每次 `tick()` 消费 | 不引入后台线程，行为一致，调试成本低 |
| 定时任务 | 独立定时任务 | 每次进入菜单/操作后 `Scheduler.tick()` | 课程演示不需要常驻调度器；时间判定仍以服务器时间为准 |

## 4. 关键实现决策

1. **名额原子扣减**：`TicketService.try_occupy` 执行
   `UPDATE ticket_type SET occupied = occupied + 1 WHERE id = ? AND occupied < capacity`，
   影响行数为 1 才是成功；并发测试验证 8 个线程抢 1 个名额只有 1 个成功。
2. **事务边界**：`Database.transaction()` 使用 `BEGIN IMMEDIATE`；名额、报名记录、
   审计在同一事务；失败回滚。SQLite WAL + `busy_timeout` 处理并发写。
3. **报名幂等**：`registration.request_id` 唯一 + `(account_id, session_id)` 唯一；
   重复请求返回首次记录，不再扣名额。
4. **候补递补**：退票写 `outbox_message(CapacityReleased)`；`PromotionService` 消费事件：
   取队首 → 原子占用 → 生成报名记录 → 更新候补状态。D3 依赖 D4 入队，D4 不反向依赖 D3。
5. **状态机**：活动、报名、候补、检票状态均为封闭枚举；非法转换抛业务异常；
   终态不可再变；场次结束由 `Scheduler` 推进“未检票/正常结束”。
6. **权限与数据范围**：服务层统一调用 `PermissionService`；报名/候补每次从数据库
   重新读取账号状态，封禁立即生效；手机号仅本人和管理员可见，组织者/检票员看遮挡版。
7. **审计同事务**：关键操作在业务事务内写 `audit_log`；预期失败（名额已满、重复报名）
   在回滚后用独立事务写失败原因。
8. **通知不写审计**：通知由业务事务内写 `notification`，符合 REQ-028“通知本身不留痕”。

## 5. 与实验二设计不一致之处

| 项目 | 设计 | 实现 | 处理 |
|---|---|---|---|
| 数据库 | MySQL 8.0 | SQLite 3 | 课程桌面程序；保留事务/约束/原子更新；SQL 方言差异不影响规则 |
| UI | 9 屏 Web UI | 四角色终端菜单 | 手册不强制 GUI；终端覆盖同样业务流程 |
| 定时任务 | 独立定时任务 | 每次 `tick()` | 演示时进入菜单即推进；测试用 `ManualClock` 精确控制 |
| 活动时间 | 活动级 `time` | 由场次开始/结束推导；场次增加 `end_time` | 统计和状态推进更精确；创建向导只建一个场次 |
| 修改审核 | 时间/地点/容量/票价 | 地点、场次时间、容量/票价走审核；名称/描述/封面/标签直接生效 | 名称在需求中未明确归类，按“表面信息”处理 |
| 候补并发 | 事件驱动 + 重试 | 同步消费 Outbox；占用失败则等下一次释放事件 | 单进程课程项目；FIFO 与不超发规则保持一致 |
| 审计保存期 | 6 个月 | 只追加不删除，不做到期归档 | 至少保留 6 个月；课程不实现归档任务 |
| 性能指标 | 1 万条/50 并发/95% 1 秒 | 提供并发正确性测试，未做正式压测 | 在报告中说明为部分实现 |
